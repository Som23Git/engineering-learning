# Day 001 — HTTP

Date: 2026-05-03

## Simple Explanation

HTTP stands for **Hypertext Transfer Protocol**.

It is the protocol most web clients and servers use to communicate.

When a browser, mobile app, frontend application, backend service, or command-line tool wants to request data from a server, it often uses HTTP.

Example:

```text
Client: "GET /users/123"
Server: "200 OK, here is the user data"
```

HTTP is a **request-response protocol**:

1. A client sends a request.
2. A server processes it.
3. The server sends back a response.

Common clients include:

- Web browsers
- Mobile apps
- Frontend JavaScript applications
- Backend services calling other backend services
- Tools like `curl`, Postman, and Insomnia

Common servers include:

- REST APIs
- Web applications
- Load balancers
- API gateways
- Reverse proxies
- Microservices

---

## Why It Exists

HTTP exists to provide a standard way for systems to exchange information over a network.

Before HTTP, different systems needed custom communication rules. HTTP gave the web a shared language.

It defines things like:

- How a client asks for a resource
- How a server responds
- How status codes communicate success or failure
- How metadata is sent using headers
- How request and response bodies are structured
- How caching, authentication, compression, and redirects work

Without HTTP, every application would need to invent its own communication format.

For backend and platform engineers, HTTP is important because many production systems are built around it:

- APIs
- Internal microservice communication
- Health checks
- Load balancers
- Webhooks
- Authentication flows
- Observability tools
- Cloud platform services

---

## Real-World Analogy

Think of HTTP like ordering food at a restaurant.

You are the **client**.

The kitchen is the **server**.

You make a request:

```text
"I would like burger #123."
```

The kitchen responds:

```text
"200 OK. Here is your burger."
```

Sometimes things go wrong:

```text
"404 Not Found. We do not serve that item."
```

```text
"500 Internal Server Error. Something broke in the kitchen."
```

You can also include extra information in your request:

```text
"Authorization: I have a reservation."
"Accept: I want the response in JSON."
```

The server can include extra information in its response:

```text
"Content-Type: application/json"
"Cache-Control: cache this for 60 seconds"
```

HTTP gives both sides a predictable structure for communication.

## Technical Explanation

HTTP is an **application-layer protocol**.

That means it operates at the top level of networking, where applications communicate with each other.

A simplified network stack looks like this:

```text
Application Layer: HTTP
Transport Layer: TCP or QUIC
Network Layer: IP
Link Layer: Ethernet / Wi-Fi
```

Most traditional HTTP traffic uses **TCP**, which stands for **Transmission Control Protocol**.

Modern HTTP/3 uses **QUIC**, a newer transport protocol built on top of **UDP**, which stands for **User Datagram Protocol**.

### HTTP Request Structure

An HTTP request usually has:

1. A method
2. A path
3. Headers
4. An optional body

Example:

```http
POST /users HTTP/1.1
Host: api.example.com
Content-Type: application/json
Authorization: Bearer abc123

{
  "name": "Ava",
  "email": "ava@example.com"
}
```

### HTTP Response Structure

An HTTP response usually has:

1. A status code
2. Headers
3. An optional body

Example:

```http
HTTP/1.1 201 Created
Content-Type: application/json
Location: /users/123

{
  "id": 123,
  "name": "Ava",
  "email": "ava@example.com"
}
```

---

### Common HTTP Methods

HTTP methods describe the action the client wants to perform.

| Method | Meaning | Common Use |
|---|---|---|
| `GET` | Retrieve data | Get a user, list orders |
| `POST` | Create or submit data | Create user, submit payment |
| `PUT` | Replace a resource | Replace entire user profile |
| `PATCH` | Partially update a resource | Change user email |
| `DELETE` | Delete a resource | Delete an account |
| `HEAD` | Get headers only | Check if resource exists |
| `OPTIONS` | Ask what is allowed | Cross-Origin Resource Sharing preflight |

Example:

```http
GET /users/123
```

Means:

```text
Retrieve the user with ID 123.
```

---

### Common HTTP Status Codes

HTTP status codes tell the client what happened.

#### 2xx — Success

| Code | Meaning |
|---|---|
| `200 OK` | Request succeeded |
| `201 Created` | Resource was created |
| `204 No Content` | Request succeeded, but no response body |

#### 3xx — Redirection

| Code | Meaning |
|---|---|
| `301 Moved Permanently` | Resource has permanently moved |
| `302 Found` | Temporary redirect |
| `304 Not Modified` | Cached version is still valid |

#### 4xx — Client Errors

| Code | Meaning |
|---|---|
| `400 Bad Request` | Request is malformed |
| `401 Unauthorized` | Authentication is missing or invalid |
| `403 Forbidden` | Client is authenticated but not allowed |
| `404 Not Found` | Resource does not exist |
| `409 Conflict` | Request conflicts with current state |
| `429 Too Many Requests` | Client is being rate limited |

#### 5xx — Server Errors

| Code | Meaning |
|---|---|
| `500 Internal Server Error` | Generic server failure |
| `502 Bad Gateway` | Proxy received invalid response from upstream |
| `503 Service Unavailable` | Server is temporarily unavailable |
| `504 Gateway Timeout` | Proxy timed out waiting for upstream |

---

### Headers

HTTP headers are key-value metadata.

Example:

```http
Content-Type: application/json
Authorization: Bearer token123
Accept: application/json
User-Agent: curl/8.0
```

Common request headers:

| Header | Purpose |
|---|---|
| `Host` | Target hostname |
| `Authorization` | Credentials or access token |
| `Content-Type` | Format of the request body |
| `Accept` | Format the client wants in response |
| `User-Agent` | Information about the client |
| `Cookie` | Browser-stored state |

Common response headers:

| Header | Purpose |
|---|---|
| `Content-Type` | Format of the response body |
| `Set-Cookie` | Ask browser to store a cookie |
| `Cache-Control` | Caching rules |
| `Location` | Redirect or newly created resource URL |
| `Retry-After` | When to retry after rate limiting or outage |

---

### Body

The body contains data sent with the request or response.

For APIs, the body is often JSON.

JSON stands for **JavaScript Object Notation**.

Example JSON body:

```json
{
  "id": 123,
  "name": "Ava"
}
```

Not every request or response has a body.

For example:

```http
GET /health
```

Often has no request body.

A successful delete may return:

```http
204 No Content
```

Which means the operation succeeded but there is no response body.

---

### HTTP Is Stateless

HTTP is considered **stateless**.

That means each request is independent.

The server does not automatically remember previous requests from the same client.

For example:

```text
Request 1: Login
Request 2: Get my profile
```

The second request must include some way to prove who the user is.

Common ways to handle identity across requests:

- Cookies
- Session IDs
- JSON Web Tokens, also called JWTs
- API keys
- OAuth access tokens

Statelessness makes HTTP easier to scale because any server instance can handle any request, assuming shared state is stored externally.

For example:

```text
Client
  -> Load Balancer
    -> API Server 1
    -> API Server 2
    -> API Server 3
```

If all authentication/session data is available to each API server, the load balancer can send requests to any instance.

---

### HTTP vs HTTPS

HTTPS stands for **Hypertext Transfer Protocol Secure**.

HTTPS is HTTP over **TLS**, which stands for **Transport Layer Security**.

TLS provides:

- Encryption
- Server identity verification
- Protection against tampering

Without HTTPS, data can be read or modified by attackers on the network.

In production, public HTTP APIs should almost always use HTTPS.

Example:

```text
http://api.example.com     Not encrypted
https://api.example.com    Encrypted with TLS
```

---

### HTTP Versions

| Version | Notes |
|---|---|
| HTTP/1.1 | Very common; text-based; supports persistent connections |
| HTTP/2 | Binary protocol; supports multiplexing multiple streams over one connection |
| HTTP/3 | Uses QUIC over UDP; improves performance in some network conditions |

As a backend beginner, you should understand HTTP/1.1 first because its request-response format is easiest to inspect and reason about.

## Practical Example

Here is a small HTTP API example using Node.js with Express.

Express is a web framework for Node.js.

```js
const express = require("express");

const app = express();

app.use(express.json());

const users = {
  123: {
    id: 123,
    name: "Ava",
    email: "ava@example.com"
  }
};

app.get("/health", (req, res) => {
  res.status(200).json({ status: "ok" });
});

app.get("/users/:id", (req, res) => {
  const user = users[req.params.id];

  if (!user) {
    return res.status(404).json({
      error: "User not found"
    });
  }

  res.status(200).json(user);
});

app.post("/users", (req, res) => {
  const { name, email } = req.body;

  if (!name || !email) {
    return res.status(400).json({
      error: "name and email are required"
    });
  }

  const id = Date.now();

  const user = {
    id,
    name,
    email
  };

  users[id] = user;

  res.status(201).json(user);
});

app.listen(3000, () => {
  console.log("API listening on http://localhost:3000");
});
```

Example requests:

```bash
curl http://localhost:3000/health
```

Response:

```json
{
  "status": "ok"
}
```

Create a user:

```bash
curl -X POST http://localhost:3000/users \
  -H "Content-Type: application/json" \
  -d '{"name":"Mina","email":"mina@example.com"}'
```

Get a user:

```bash
curl http://localhost:3000/users/123
```

This example demonstrates:

- `GET`
- `POST`
- JSON request bodies
- JSON response bodies
- `200 OK`
- `201 Created`
- `400 Bad Request`
- `404 Not Found`

## Where This Appears in Production

HTTP appears almost everywhere in backend and platform engineering.

### Public APIs

Example:

```text
Mobile App -> HTTPS -> api.company.com -> Backend API
```

The mobile app calls HTTP endpoints to log in, fetch data, and submit changes.

---

### Internal Microservices

Example:

```text
Orders Service -> HTTP -> Payments Service
```

A backend service may call another backend service over HTTP.

Example request:

```http
POST /payments
Content-Type: application/json

{
  "orderId": "ord_123",
  "amount": 4999,
  "currency": "USD"
}
```

---

### Load Balancers

A load balancer receives HTTP requests and forwards them to healthy backend servers.

Example:

```text
Client
  -> Load Balancer
    -> API Server A
    -> API Server B
    -> API Server C
```

Load balancers often use HTTP health checks:

```http
GET /health
```

If a server returns `200 OK`, it is considered healthy.

If it returns `500` or times out, traffic may stop being sent to it.

---

### Reverse Proxies

A reverse proxy sits in front of backend services.

Common reverse proxies:

- NGINX
- Envoy
- HAProxy
- Traefik

They can handle:

- TLS termination
- Routing
- Compression
- Rate limiting
- Request logging
- Authentication
- Load balancing

Example:

```text
Client -> NGINX -> Backend API
```

---

### API Gateways

An API gateway is a managed or centralized HTTP entry point for APIs.

It can handle:

- Authentication
- Authorization
- Rate limiting
- Request validation
- Routing to services
- Metrics and logs

Cloud examples:

- Amazon API Gateway
- Google Cloud API Gateway
- Azure API Management
- Kong
- Apigee

---

### Kubernetes

Kubernetes commonly uses HTTP for:

- Readiness probes
- Liveness probes
- Ingress routing
- Service-to-service traffic
- Metrics endpoints

Example readiness probe:

```yaml
readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080
```

If the endpoint returns success, Kubernetes can route traffic to the pod.

---

### Observability

Observability systems often collect HTTP metrics such as:

- Request count
- Error rate
- Latency
- Status code distribution
- Request size
- Response size

Common metric names:

```text
http_requests_total
http_request_duration_seconds
http_5xx_errors_total
```

These metrics help engineers answer:

- Is the API healthy?
- Are users receiving errors?
- Which endpoint is slow?
- Did the latest deployment increase latency?

## Common Beginner Mistakes

### 1. Confusing HTTP with the Internet

HTTP is not the entire internet.

HTTP is one protocol that runs on top of lower-level networking protocols.

Other protocols include:

- DNS: Domain Name System
- TCP: Transmission Control Protocol
- UDP: User Datagram Protocol
- SMTP: Simple Mail Transfer Protocol
- SSH: Secure Shell

---

### 2. Thinking `POST` Always Means Create

`POST` is commonly used for creation, but it means "process this request body according to the server's rules."

Examples:

```http
POST /users
POST /login
POST /payments/charge
POST /reports/generate
```

Not all `POST` requests create a simple resource.

---

### 3. Using the Wrong Status Codes

Common examples:

Bad:

```text
Returning 200 OK for an error.
```

Better:

```text
400 Bad Request for invalid input.
404 Not Found for missing resource.
401 Unauthorized for missing or invalid authentication.
403 Forbidden for authenticated user without permission.
500 Internal Server Error for unexpected server failure.
```

Status codes are part of your API contract.

---

### 4. Ignoring Timeouts

HTTP requests can hang.

Production clients should set timeouts.

Bad assumption:

```text
The server will always respond quickly.
```

Better assumption:

```text
The network can fail.
The server can be slow.
The request may time out.
```

Timeouts are critical in distributed systems because one slow dependency can slow down many services.

---

### 5. Not Understanding Idempotency

An operation is **idempotent** if repeating it produces the same final result.

Usually idempotent:

```http
GET /users/123
PUT /users/123
DELETE /users/123
```

Usually not idempotent:

```http
POST /payments
```

Why this matters:

If a client retries a request after a timeout, duplicate side effects may happen.

Example:

```text
Client sends payment request.
Server charges card.
Response times out.
Client retries.
Server charges card again.
```

Payment APIs often use an **idempotency key** to prevent duplicate charges.

Example:

```http
POST /payments
Idempotency-Key: abc-123
```

---

### 6. Putting Sensitive Data in URLs

URLs are often logged by:

- Browsers
- Proxies
- Load balancers
- Servers
- Monitoring tools

Bad:

```http
GET /reset-password?token=secret-token
```

Better:

```http
POST /reset-password
Content-Type: application/json

{
  "token": "secret-token",
  "newPassword": "..."
}
```

Even request bodies can be logged accidentally, but URLs are especially risky.

---

### 7. Forgetting That HTTP Is Stateless

The server does not automatically know who the client is.

Every request that requires identity needs credentials, such as:

```http
Authorization: Bearer token
```

or a cookie.

---

### 8. Treating 5xx and 4xx Errors the Same

A `4xx` error usually means the client sent a bad or unauthorized request.

A `5xx` error usually means the server or upstream dependency failed.

This matters for retries.

Usually safe to retry:

```text
502 Bad Gateway
503 Service Unavailable
504 Gateway Timeout
```

Usually not useful to retry without changing the request:

```text
400 Bad Request
401 Unauthorized
403 Forbidden
404 Not Found
```

## Related Concepts

- **URL**: Uniform Resource Locator. The address of a resource.
- **URI**: Uniform Resource Identifier. A broader identifier for a resource.
- **DNS**: Domain Name System. Resolves domain names to IP addresses.
- **IP**: Internet Protocol. Routes packets between machines.
- **TCP**: Transmission Control Protocol. Reliable transport protocol.
- **UDP**: User Datagram Protocol. Lightweight transport protocol without built-in reliability.
- **TLS**: Transport Layer Security. Encrypts network communication.
- **HTTPS**: HTTP over TLS.
- **REST**: Representational State Transfer. An architectural style often used with HTTP APIs.
- **JSON**: JavaScript Object Notation. Common data format for APIs.
- **Cookies**: Small pieces of data stored by browsers and sent with requests.
- **CORS**: Cross-Origin Resource Sharing. Browser security mechanism controlling cross-origin HTTP requests.
- **Caching**: Storing responses to avoid repeated work.
- **Reverse Proxy**: Server that sits in front of backend services.
- **Load Balancer**: Distributes traffic across multiple backend instances.
- **API Gateway**: Central entry point for API traffic.
- **Webhooks**: HTTP callbacks sent when events happen.
- **gRPC**: Remote Procedure Call framework often using HTTP/2.
- **WebSocket**: Protocol for persistent bidirectional communication.

## Interview-Level Explanation

HTTP is an application-layer, request-response protocol used for communication between clients and servers. A client sends an HTTP request containing a method, path, headers, and optionally a body. The server returns an HTTP response containing a status code, headers, and optionally a body.

HTTP methods describe the intended operation. For example, `GET` retrieves data, `POST` submits data, `PUT` replaces a resource, `PATCH` partially updates a resource, and `DELETE` removes a resource.

HTTP status codes describe the result. `2xx` means success, `3xx` means redirection, `4xx` means client error, and `5xx` means server error.

HTTP is stateless, meaning each request is independent. Authentication or session context must be provided with each request, commonly through cookies, API keys, or bearer tokens.

In production systems, HTTP is used by public APIs, internal microservices, load balancers, reverse proxies, API gateways, Kubernetes probes, and observability systems. HTTPS secures HTTP using TLS, providing encryption and identity verification.

Important engineering concerns include choosing correct status codes, setting timeouts, handling retries safely, understanding idempotency, securing sensitive data, using caching correctly, and monitoring latency and error rates.

A strong backend engineer should understand not only how to create endpoints, but also how HTTP behaves across real infrastructure such as proxies, gateways, load balancers, and distributed services.
